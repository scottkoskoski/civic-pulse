# Lesson 5 — Marts & Star Schema

> **Goal:** Build the dimensional models that BI tools will hit:
> three conformed dimensions (date, location, offense), one central
> fact, all joined through surrogate keys.
>
> **Time:** ~3 hours.
>
> **You'll come away knowing:** what a star schema is and why it's
> still the dominant analytical pattern, how dbt seeds work, how to
> build a derived dimension from a staging model, how to construct
> surrogate keys safely (including NULL handling), and what
> `relationships` tests prove.

---

## What problem are we solving?

Staging gives us a clean, typed copy of incident rows. That's the
right shape for further transformation but the wrong shape for
analytics.

A BI user wants to answer questions like:

- "How many burglaries happened in Ward 5 in Q3 2023?"
- "Which precinct had the largest year-over-year change in assaults?"
- "Plot incidents by hour of day, faceted by offense category."

Every one of those questions involves grouping by a *thing* (a
category, a location, a date range) and counting or aggregating
incidents. If staging is what we expose to BI, every dashboard has
to repeat the same `WHERE` clauses and `GROUP BY` patterns and
typing decisions. We want a layer that hides that work.

The standard answer is a **star schema**:

- A central **fact table** (`fct_incidents`) — one row per
  business event, with foreign keys to dimensions and numerical
  measures.
- Several **dimension tables** (`dim_date`, `dim_location`,
  `dim_offense`) — one row per distinct value of an attribute,
  with descriptive columns that don't change much.
- Each dimension joins to the fact on a **surrogate key** — a
  short, stable identifier generated by the data team rather than
  inherited from the source.

The fact is wide and tall; each dimension is narrow and short.
Queries are predictable: filter on a dimension, group on a
dimension, aggregate from the fact.

---

## Concepts introduced

- **Star schema.** A central fact table surrounded by dimension
  tables, joined through foreign keys. Named for the visual shape
  in an ER diagram. Coined by Ralph Kimball in the 1990s, still
  the default analytical pattern.

- **Dimension table (dim).** A table of unique values for a
  categorical attribute, plus descriptive columns. Wide on
  attributes, short on rows. Examples in our project:
  `dim_date` (one row per calendar day), `dim_location` (one row
  per ward/precinct/council combo), `dim_offense` (one row per
  category/description combo).

- **Fact table.** A table of business events, one row per event,
  with foreign keys pointing at every dimension and numerical
  measures (counts, amounts, durations) in the row body.

- **Conformed dimension.** A dimension shared across multiple
  fact tables. `dim_date` is the canonical example — every fact
  table in any data warehouse references the same calendar
  dimension. Conformed dims make cross-fact analysis sane.

- **Surrogate key.** An identifier generated by the analytics
  layer rather than inherited from the source. We use an md5 hash
  of the dim's natural-key columns. Why surrogate over natural?
  Surrogate keys are uniform width, hide source-system messiness
  (composite keys, varying types, NULLs), and survive source
  renames.

- **Degenerate dimension.** A dimension whose only useful column
  *is* the key itself — typically the source-system identifier
  for the event. `incident_id` on `fct_incidents` is degenerate:
  we don't have other attributes that describe it. Carrying it on
  the fact (rather than spinning up `dim_incident`) is the right
  call when the dim would have one and only one column.

- **dbt seed.** A small CSV checked into the repo and loaded into
  the warehouse by `dbt seed`. Seeds occupy the same lineage
  position as a model — they can be `ref()`d, tested, documented,
  and joined to. We use one for `dim_date`.

- **`relationships` test.** A generic test that asserts every
  value in the child column exists in the parent column. Foreign-
  key check by another name. We attach these to fact-table FK
  columns to prove the join never orphans.

## The build, narrated

Five artifacts land this lesson: a seed CSV, three model files,
and a schema YAML. We'll cover them in build order, since the
fact depends on the dims.

### 1. `seeds/dim_date.csv`

```
date_key,full_date,year,quarter,month_num,month_name,day_of_month,day_of_week,day_name,is_weekend,week_of_year
20150101,2015-01-01,2015,1,1,January,1,4,Thursday,false,1
20150102,2015-01-02,2015,1,1,January,2,5,Friday,false,1
...
```

The file covers 2015-01-01 through 2030-12-31. That's about
5,845 rows and ~340 KB — small enough to commit comfortably.

**Generated by a one-shot Python script**, not by SQL. The
generation logic is too imperative for SQL (loop over a date
range, derive ten columns per row, write CSV). Once generated,
the artifact is static. The script lives in this lesson's docs
because we're unlikely to regenerate it; if the range ever needs
extension, copy-and-extend.

Here's the generator (run from the repo root if you ever need to
recreate it):

```python
from datetime import date, timedelta
import csv

start = date(2015, 1, 1)
end   = date(2030, 12, 31)
months = ["", "January", "February", "March", "April", "May", "June",
          "July", "August", "September", "October", "November", "December"]
days   = ["Monday","Tuesday","Wednesday","Thursday","Friday","Saturday","Sunday"]

with open("seeds/dim_date.csv", "w", newline="") as f:
    w = csv.writer(f)
    w.writerow([
        "date_key","full_date","year","quarter","month_num",
        "month_name","day_of_month","day_of_week","day_name",
        "is_weekend","week_of_year",
    ])
    d = start
    while d <= end:
        iso = d.isoweekday()
        w.writerow([
            int(d.strftime("%Y%m%d")),
            d.isoformat(),
            d.year,
            (d.month - 1) // 3 + 1,
            d.month, months[d.month],
            d.day, iso, days[iso - 1],
            "true" if iso in (6, 7) else "false",
            d.isocalendar().week,
        ])
        d += timedelta(days=1)
```

**Why seed the date dimension instead of generating it in SQL?**
You can generate dates inline with DuckDB's `generate_series` and
the equivalent in Snowflake, then derive columns with date
functions. We don't, because:

- A seed is a *fixed artifact*. Two contributors will get
  identical dim_date rows on every machine. SQL generation can
  drift if anyone tweaks the WHERE clause.
- The seed is reviewable in git. A `select ... from generate_series`
  hidden in a model is harder to spot if it's wrong.
- Date dimensions barely change. The 5,000-row seed cost is
  trivial; the determinism is valuable.

The tradeoff: extending the range requires regenerating the CSV
and committing the diff. For a date dim that's once-per-decade
work.

### 2. `models/marts/dim_location.sql` and `models/marts/dim_offense.sql`

Both follow the same pattern: `select distinct` over the
natural-key columns from staging, then hash to produce a
surrogate key.

```sql
with incidents as (
    select * from {{ ref('stg_memphis__incidents') }}
),
distinct_locations as (
    select distinct ward, precinct, council_district from incidents
),
with_key as (
    select
        md5(
            coalesce(ward, '__null__')             || '|' ||
            coalesce(precinct, '__null__')         || '|' ||
            coalesce(council_district, '__null__')
        ) as location_key,
        ward, precinct, council_district
    from distinct_locations
)
select * from with_key
```

Three details worth pulling out:

**`coalesce(col, '__null__')` before hashing.** `md5(NULL || 'x')`
is NULL in most SQL dialects — concatenating with a NULL nukes the
whole expression. Without the coalesce, every dim row where any
key column is NULL would get a NULL surrogate key. That collides
all such rows together and fails the `unique` test. Coalescing to
a sentinel string makes the hash stable and distinct per
combination.

**`'|'` as a separator between concatenated columns.** Without a
separator, the values `("ab", "cd")` and `("a", "bcd")` would both
hash as `md5("abcd")` — a collision. The pipe character is unlikely
to appear in real data; it disambiguates without escaping.

**We keep the all-NULL row.** Some teams filter out
`(NULL, NULL, NULL)` rows from dims on the theory that they
represent missing data. We don't, because:

- The all-NULL combination is a real state of the world for
  incidents reported without administrative location. Including
  it lets BI users analyze "incidents with no recorded location"
  as a discrete group.
- Filtering would cause the corresponding fact rows to fail the
  `relationships` test — they'd reference a `location_key`
  that doesn't exist.

`dim_offense` follows the identical pattern with
`(offense_category, offense_description)` as the natural key.

### 3. `models/marts/fct_incidents.sql`

The fact joins staging to each dim and emits one row per incident
with the surrogate FKs substituted for natural keys:

```sql
joined as (
    select
        i.incident_id,
        (year(i.offense_date) * 10000
       + month(i.offense_date) * 100
       + day(i.offense_date))                  as date_key,
        l.location_key,
        o.offense_key,
        i.offense_datetime, i.latitude, i.longitude, i.street_address,
        1::int                                 as incident_count
    from incidents i
    left join location l on
       coalesce(i.ward, '__null__') = coalesce(l.ward, '__null__')
       and coalesce(i.precinct, '__null__') = coalesce(l.precinct, '__null__')
       and coalesce(i.council_district, '__null__') = coalesce(l.council_district, '__null__')
    left join offense o on
       coalesce(i.offense_category, '__null__') = coalesce(o.offense_category, '__null__')
       and coalesce(i.offense_description, '__null__') = coalesce(o.offense_description, '__null__')
)
```

The bits that warrant explanation:

**date_key construction by primitives.** DuckDB's `strftime` would
be cleaner (`cast(strftime(offense_date, '%Y%m%d') as integer)`)
but is DuckDB-specific. Snowflake uses `to_char` with similar
intent. To keep the model portable across both warehouses without
a Jinja branch, we build the integer from `year() * 10000 +
month() * 100 + day()`. Both adapters support those functions
identically.

**The coalesce-based join.** Same NULL-sentinel pattern used to
build the dim's surrogate key. If a staging row has `ward=NULL`,
it joins to the dim row whose `ward` is also NULL — because both
sides went through `coalesce(..., '__null__')` first. Without this,
a `left join ... on i.ward = l.ward` would never match NULL-to-NULL,
since `NULL = NULL` is itself NULL (unknown). The relationships
tests in `_marts_models.yml` confirm the join never orphans.

**`incident_count` literal 1.** The docstring on the .sql file
covers the rationale. Short version: BI tools express counts as
sums of an explicit measure column; we provide one rather than
forcing every dashboard to invent its own.

### 4. `models/marts/_marts_models.yml`

The marts-layer schema YAML, structurally identical to
`_stg_models.yml` but covering seeds and four models. Two pieces
worth highlighting:

```yaml
- name: date_key
  data_tests:
    - not_null
    - relationships:
        to: ref('dim_date')
        field: date_key
```

The `relationships` test compiles to a query that returns rows
where the child FK can't be found in the parent. Specifically:

```sql
select date_key as from_field
from marts.fct_incidents
where date_key is not null
  and date_key not in (select date_key from marts.dim_date)
```

A non-empty result is a test failure with the offending values
printed. This is the foreign-key check the warehouse won't enforce
on its own.

We attach `relationships` to all three FK columns on the fact.
If any FK ever fails, it's almost always one of:

- The dim is missing a value the fact references (e.g., the date
  spine doesn't reach far enough in either direction).
- The join logic in the fact is wrong.
- The dim's surrogate-key construction differs from how the fact
  computes the same hash. (We've been careful to use the same
  coalesce pattern in both places. Lesson 6's `generate_surrogate_key`
  macro is partly about eliminating this risk.)

## Decisions & tradeoffs

### Why three dims, not more or fewer?

The minimum useful star schema has the dims you'll actually filter
or group by. For Memphis crime data:

- **Date** — every incident has a date; every analysis groups by
  some date period. Mandatory.
- **Location** — most analyses care about *where* the incident
  happened. Mandatory.
- **Offense** — most analyses care about *what* kind of incident.
  Mandatory.

We could add:

- **Day-of-week dim.** Redundant — already an attribute of
  `dim_date`.
- **Time-of-day dim.** Worth considering for hour-level analysis,
  but `offense_datetime` on the fact handles it. Hour-of-day is
  a 24-value distinct set; pulling it into a dim is overkill.
- **Reporting agency dim.** MPD is the only agency for this
  dataset; useless as a dim of cardinality 1.

We start with what's necessary; later lessons or extensions can
add more.

### Why `md5` for the surrogate key?

Three popular choices for dbt surrogate keys:

1. **`md5`** of the concatenated natural-key columns. Returns a
   32-character hex string. Widely supported across warehouses.
   What we use.
2. **Sequential integer** via `row_number() over (order by ...)`.
   Compact, sortable, but order-dependent — re-running the model
   can shuffle keys, breaking fact-table FK matches.
3. **`generate_surrogate_key`** from `dbt_utils`. Wraps md5 with
   correct handling of types and NULLs across warehouses. Lesson 6
   adopts it.

We pick `md5` directly in Lesson 5 so the mechanics are visible
(coalesce, separator, exact column order). Lesson 6 swaps to the
utility once you know what it does.

### Materialization: table, not view, for everything in marts

Marts get queried by BI tools — possibly many times per second
during a busy dashboard session. Re-running the underlying SQL on
every query (which is what a view does) wastes compute. Tables
materialize once per `dbt run` and serve subsequent queries from
storage. The folder-default `+materialized: table` in
`dbt_project.yml` covers this without per-model config.

### Why is `dim_date` a seed and not a SQL model?

Covered above. Short version: determinism + git-reviewability +
the dim doesn't change.

### Why no surrogate key on dim_date?

`dim_date.date_key` is YYYYMMDD as an integer. That's already a
natural key with the properties of a surrogate (compact, uniform,
stable). We use it as-is. Hashing it would just make the join
slower.

### NULL-bearing dims = surprising-but-correct

Some teams insist dimensions don't have NULL attribute values —
the typical pattern is to substitute a sentinel like `'Unknown'`
during the dim build. We didn't, because:

- Substituting a sentinel hides the missingness from BI users.
  Filtering "WHERE ward IS NOT NULL" stops working as a discovery
  pattern.
- The sentinel can collide with legitimate values if you're not
  careful.
- The surrogate-key construction already substitutes a sentinel
  *for the hash*. The displayed value stays NULL. Best of both.

This is a judgment call; either approach is defensible.

## Run it

### Step 1 — Load the seed

```bash
dbt seed
```

Expected output (single seed):

```
1 of 1 START seed file marts.dim_date ........................ [RUN]
1 of 1 OK loaded seed file marts.dim_date ..................... [INSERT 5845 in 0.10s]
```

dbt creates `marts.dim_date` from the CSV by inferring types from
the file. Re-running `dbt seed` is idempotent (TRUNCATE + INSERT,
or CREATE OR REPLACE depending on adapter).

### Step 2 — Build everything

```bash
dbt build
```

`dbt build` runs in dependency order. You'll see something like:

```
1 of 7 START seed file marts.dim_date ....................... [RUN]
1 of 7 OK loaded seed file marts.dim_date ................... [INSERT 5845 ...]
2 of 7 START sql view model staging.stg_memphis__incidents .. [RUN]
2 of 7 OK created sql view model staging.stg_memphis__incidents [OK ...]
3 of 7 START test not_null_stg_memphis__incidents_incident_id [RUN]
3 of 7 PASS not_null_stg_memphis__incidents_incident_id ..... [PASS ...]
... (staging tests)
4 of 7 START sql table model marts.dim_location ............. [RUN]
4 of 7 OK created sql table model marts.dim_location ........ [OK ...]
5 of 7 START sql table model marts.dim_offense .............. [RUN]
6 of 7 START sql table model marts.fct_incidents ............ [RUN]
... (marts tests including relationships)
```

`dbt` runs models in dependency order but parallelizes independent
ones (dim_location and dim_offense build in parallel; fct_incidents
waits for both).

### Step 3 — Sanity-check the data

```bash
duckdb civic_pulse.duckdb
```

```sql
-- Row counts
select count(*) from marts.dim_date;        -- 5,845
select count(*) from marts.dim_location;    -- ~50-100
select count(*) from marts.dim_offense;     -- ~100-300
select count(*) from marts.fct_incidents;   -- equals staging.stg_memphis__incidents

-- Pull a sample
select * from marts.fct_incidents limit 5;

-- Try an analytical query (proves the star schema works end-to-end)
select
    d.year,
    o.offense_category,
    sum(f.incident_count) as incidents
from marts.fct_incidents f
join marts.dim_date    d using (date_key)
join marts.dim_offense o using (offense_key)
where d.year between 2022 and 2024
  and o.offense_category is not null
group by 1, 2
order by 1, 3 desc
limit 20;
```

### Step 4 — Re-view the docs

```bash
dbt docs generate
dbt docs serve
```

The lineage graph now has structure: source → staging → three
dims + one fact, with `dim_date` floating in as a seed. This is
your most useful navigation tool from here forward.
